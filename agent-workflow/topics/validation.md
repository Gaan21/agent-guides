# Validation and closure

Applies to changed work, failed checks and closure. Depends on the [entry](../ENTRY.md)
and the [reading contract](reading.md). Stack/project requirements determine checks;
this document does not install a runner or invent universal technology commands.

## Use the actual checks

- Establish acceptance, scope, explicit non-goals and required checks for the actual
  package/root. Documentation-only changes do not require unrelated code tools.
  Unknown required checks are a missing input, not an empty validation obligation.
- Factory work uses its existing tools, checkpoints and evidence. Reuse evidence
  delivered by that mechanism; do not duplicate a pipeline or bypass its reviewer.
- Manual work runs applicable documented formatting, lint, type/build and relevant
  tests, including required checkpoints/final checks. Do not replace a stack gate
  with a generic checklist or let filtered output conceal a failed process.
- Report each command, scope and actual exit/result. Separate passed, failed,
  skipped and not-run, with reasons and unavailable prerequisites. Written tests,
  configuration presence and a claimed clean summary are not executed evidence.
- Check intended behavior and failures, not just formatting. A clean analyzer is
  not proof of product correctness. Where an approved offline flow accepts a
  durable local write, do not present that as remote acknowledgment.

## Blocked work

- A required check that fails or cannot run blocks closure and commit/push. Preserve
  its output, identify the affected scope and missing tool/input/access, and consult
  the owner or existing host blocked-work flow. Never fabricate success.
- Do not suppress lint, weaken a test/baseline, skip a guard or add a generic TODO
  merely to close. Suppressions and invariant exceptions require explicit applicable
  approval and the project's justification, evidence and recovery obligations.
- Safe investigation may continue within scope, but does not authorize publication
  of unvalidated work. Report unresolved contracts and validation limits honestly.

## Closeout evidence

- Confirm delivered behavior against acceptance and non-goals; list exact changed
  files, checks/results, omissions, unresolved issues and residual risks. Keep secrets
  and sensitive data out of changes, logs and summaries.
- Honor applicable product knowledge, help, disclosure and closeout contracts; read
  their local authority when behavior may change. This generic bundle neither defines
  a product's markers nor waives those obligations when no task file exists.
- Offer independent review when useful under [review](review.md); no mandatory
  extra model, fanout, installation or result file is introduced.
- Factory closure/review/publication remains with the host. Manual validated closure
  performs scoped commit/push under the entry's authorization boundary; leave unrelated
  work intact and report local commit and remote push outcomes separately.
- A review offer or agent claim does not establish acceptance. Read-only advice or
  research does not automatically become a development change to commit.
