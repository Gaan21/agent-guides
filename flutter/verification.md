# Implementation, control evidence and closeout

Applies throughout scoped Flutter work and guidance reviews/updates.
Read [conventions](conventions.md) and affected topics before applicable edits.

## Start and implement

- Read native authority/task preloads, inspect Git changes, preserve unrelated work.
  Use the same retained revision/guidance selection/engine/policy/overlay identity
  as review where the host retains those fields. Never independently fetch latest.
- Identify changed boundaries and owners; inspect actual APIs/contracts and effective
  lint registrations/options/include chain/severities/exclusions. Missing required
  contracts block affected implementation rather than justify invented components.
- Choose cohesive responsibilities and approved validation commands at an explicit
  package root. Follow native checkpoints and final gates; do not install historical
  scripts, hooks, plugins, wrappers or a second factory pipeline from documentation.
- Formatting, effective lint and applicable analysis remain required checks; do not
  impose a fixed per-file command. A factory runs them through its approved mechanism;
  manual work uses block feedback and complete final validation, respecting stricter
  local requirements and the installed tool versions.
- Use locked approved toolchains. Generate code/mocks only when required. Do not
  upgrade dependencies because a page advertises a newer SDK or uses placeholder
  dependency versions; inspect compatibility and preserve selections/rollback.

## Evidence, not enforcement claims

Record separately: available package/full revision/SDK; actual diagnostic predicate,
scope/exceptions/known misses; real plugin registration; dependency/configuration
identity/include chain/options/severity/exclusions; explicit root/command/status/
output/valid-invalid cases; residual tests/types/components/review and unresolved gaps.
Separate packages and consumers. YAML names, source files and prose fixtures do not
prove installed activation, executed checks, model compliance or native enforcement.

Test gates against clean input, known violation, crash, missing SDK/config/package,
unrelated diagnostics, generated paths and no-touched cases. Filtering output to no
matches must not swallow subprocess failure. Missing mandatory configuration is not
a clean pass. Reason tags, key arguments, annotations and close/super-call presence
prove only bounded syntax, not safe background work, stable identity, deep value
semantics, confidentiality or all-path ownership. Preserve explicit resource typing
until actual cleanup evidence supports any approved relaxation.

## Close and update

- Report passed/failed/skipped/not-run separately, command/status/root and reasons,
  changed files, unresolved contracts and residual risk. Analyzer success is not
  product correctness. Missing/failing mandatory checks block validated closure.
- Factory host owns branch/tool/check/PR/publication flow; do not duplicate it.
  Manual validated closure performs scoped commit/push on the agreed branch without
  another prompt. Do not stage unrelated work, change agreed branches, bypass
  protections or infer merge/release/deploy/private-upload permission. Unknown mode
  or unavailable required checks go to owner/host blocked-work handling.
- Suppressions/exclusions and invariant exceptions require explicit approval and
  traceable justification plus covering/recovery evidence required by the consumer.
- A request to review guidance means inspect/report, not update pins, accept work
  or restart clients. An explicit routine update request permits approved source/pin/
  connection updates while preserving local selections and rollback. Resolve once;
  incompatible policy/source/lint upgrade or legacy migration is a separate decision.
- Already-running contexts retain delivered instructions: report restart/loading
  verification still pending. A checkout/wheel/version label is not automatically
  latest. Never alter live snapshots or silently replace local exceptions.
- Shared-rule changes need companion-linter impact review, provenance and independent
  semantic review. Keep concise English and local references; link upstream instead
  of importing tutorials/config/lint source. Do not claim historical measurements as
  fresh results or development trials as stable-release approval.
